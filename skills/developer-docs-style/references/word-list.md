# Word list

The entries from the guide's word list that writers most often get wrong. The full list is at https://developers.google.com/style/word-list. When a product's own UI or docs use a term, such as *log in*, use the product's term.

## Contents

- Filler and opinion
- UI actions
- Latin abbreviations and shorthand
- Word choice
- Modal verbs
- Ambiguous conjunctions
- Position and versions
- Inclusive terms

## Filler and opinion

| Word | Guidance |
|---|---|
| please | Don't use in instructions. Never write "please note." Use it only when you ask permission or forgiveness. |
| simple, simply, easy, easily, quick, quickly | Delete. What's simple for you might not be for the reader. |
| just | Usually filler: "BigQuery skips the row," not "BigQuery just skips the row." If the meaning needs it, write *only*, *instead*, or *previously*. |
| careful, carefully | Don't use. "Enter the API key that appears in the console," not "Make sure to enter the API key carefully." |
| proper, properly | Name the detail: "Verify that the port is open and accepting connections," not "Ensure the port is properly configured." |
| let's | Don't use. |
| wish, desire, desired | Write *want* or *need*: "Set the value to the size that you want." |

## UI actions

| Word | Guidance |
|---|---|
| click | For desktop UIs: "Click **OK**," never "click on." Hyphenate *right-click* and *double-click*. Use *tap* for mobile. |
| click here | Don't use. Write descriptive link text. |
| select | For choosing an option, selecting text, or marking a checkbox: "Select **Automatically check for updates**." |
| check, uncheck, deselect | For checkboxes, write *select* and *clear*: "Clear **Automatically check for updates**." |
| choose | Fine in general. For a UI element, write *select*. |
| hover | Don't use. Write "hold the pointer over." |
| hit | Don't use for click, press, or type. |

## Latin abbreviations and shorthand

| Word | Guidance |
|---|---|
| e.g. | Write "for example" or "such as." |
| i.e. | Write "that is." |
| etc. | Avoid. Write "problems such as instability or high latency," not "instability, high latency, etc." |
| via | Don't use. Write *through*, *by using*, or *with*. |
| and/or | Avoid, except where space is tight, such as in a table. |
| in order to | Write *to*, unless *in order to* makes the sentence clearer. |

## Word choice

| Word | Guidance |
|---|---|
| allows you to, enables you to | Write *lets you*: "The API lets you detect features in images." Use *enable* only for turning something on: "Enable the API for your project." |
| disable | Prefer *turn off*. Never use it to mean broken. |
| utilize, leverage | Write *use*. *Utilization* is fine for resource use: "When CPU utilization exceeds 75%." |
| execute | Write *run* when the meaning is the same. |
| functionality | Usually you mean *capabilities* or *features*. |
| using | Write *by using* or *that use* when it could be misread: "Remove the VMs by using the `test` tag." |
| this, that | Follow with a noun where you can: "this setting," not "this." |
| sign in, log in | Use *sign in* unless the product says *log in*. Use the two-word verb and the one-word noun. |

## Modal verbs

| Word | Guidance |
|---|---|
| may | Only for policy or legal permission. Write *might* for possibility and *can* for ability. |
| might | Possibility: "You might be prompted to enter your credentials." |
| can | Ability, an optional action, or a possible outcome: "The process can take 30 minutes." |
| must | A requirement: "You must have the Editor role." |
| should | Avoid. Write *must* or an imperative if it's required, "We recommend" if it's advice, and *can* if it's optional. State an expected result as a fact. |
| will, would | Use present tense instead, except for something that happens later. |

## Ambiguous conjunctions

| Word | Guidance |
|---|---|
| once | If you mean *after*, write *after*. |
| since, as | If you mean *because*, write *because*. |
| while | For contrast, write *although*. Keep *while* for time. |
| if ... then | Keep *then* in if-then sentences. |

## Position and versions

| Word | Guidance |
|---|---|
| above | In a document, write *earlier* or *preceding*. For versions, write *later*. |
| below | In a document, write *later* or *following*. For versions, write *earlier*. |
| higher, +, newer | For versions, write "version 2.2 or later," not "2.2 or higher" or "2.2+." |
| following | "Do the following:" works without a noun. |
| currently, now, new | Delete. "Windows isn't supported," not "Windows isn't currently supported." |

## Inclusive terms

| Word | Guidance |
|---|---|
| master, slave | Write *primary*, *main*, *controller*, *leader*, *replica*, *worker*, or *secondary*. Use the literal word only in code font. |
| whitelist, blacklist | Write *allowlist* and *denylist* (or *blocklist*), and rewrite verbs: "To deny requests from an IP address, add it to the `dos.yaml` file." |
| sanity check | Write *quick check* or *confidence check*. |
| dummy | Write *placeholder* or *sample*. |
| abort, kill, terminate | Write *stop*, *exit*, *cancel*, or *end*, except for literal signals and commands. |
| native | Write *built-in* for features. Don't use it for people. |
| he, him, his, guys | Write *they* for one person and *everyone* for a group. |
| user | Only for the user of the reader's software. Otherwise write *you*. |
